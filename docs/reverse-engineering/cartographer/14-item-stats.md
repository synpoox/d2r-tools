## 14. The map item's own stats (issue #158)

Build 93847, stamp `0x6ab3782c`, static (dump); not run in a game. The plugin reads the used item's stat list in the item-use hook, before `OpenRedPortal`, and builds the map stat plan from it (the `ItemStats` setting and `mapstats.txt` are retired, #311). The SDK has no getter for a unit's stats (`item.h` gives only `ItemInfo`), so two parts are called.

|---|---|---|---|---|

| `ItemListCopy` | `0x2f64e0` | `(list, out, max) -> count`: D2RLoader's thunk (`jmp [rip+x]`, four NOPs) into D2RLoader's replacement (`[0x3e2a300] = 0xc0de58328e0`, outside the image; its body was not read) of up to `max` pairs from the list into `out`. The dead body behind the thunk (`0x2f64ea`) is evidence for the original only: it reads the entry array at `list+0x30` and the count at `list+0x38`, copies `min(count, max)` pairs of two int32 (`{stat << 16 \| layer, value}`), returns the count copied | `FF 25 ?? ?? ?? ?? 90 90 90 90 57 48 83 EC 20 49 63 F8 48 8B DA 48 8B F1` (24 bytes, unique) | called only. The caller is the client sender `0x53a210` (call at `0x53a4de`, `r8d = 0x10`), which takes the stat as `sar eax, 0x10` of the first int32 (`0x53a536`); that is the order used here. The layer being the low 16 bits is inference. Why the `max` / 8-byte contract holds for the replacement: the image has 17 live `E8` callers of `0x2f64e0` passing `(list, buf, max)` with buffers of `max * 8` (for example `0x33eab4` and `0x33eb79` with `max 0x1ff`, `0x535178` with `0x200`, `0x423017` with `0x80`, `0x47cb3e` and `0x53a4de` with `0x10`, `0x1685c9`, `0x16941e`, `0x51cc03` and `0x51cf58` with `0x3fe`); a replacement that overran `max` would break the game's own callers. - **Which list:** the base magic list, `0x2f5b80(item, 0, 0x40)` (created with flags `0x40` at `Items.cpp:0x1900`, section 6 C). Lists on states 165 to 169 and the runeword list are not read. That a map item's affixes land in this list is inference. The match ignores only bit 13, so a state list created with flags `0x2040` (states 165 to 169) also matches `0x40`, and so would the runeword list if it carries `0x40`; if such a list comes first on the chain it is returned instead of the base magic list. Unlikely for a map item.
- **Limit:** 16 stats (the sender's own). The copy asks for up to 0x200 and the plugin cuts to 16; a longer list is cut and the log says so (exact for 17 or more).
- **Fail open:** a part off, no list, an empty list or no matching stat leaves a normal draw. Correction to section 6 C: the entries are 8 bytes (`{key, value}`), not 16; the plugin never reads the list's memory itself.
- **Mapping (unit tested):** each item stat is matched by id to the first `mapstats.txt` row (built-in pool when there is no file) whose `Stat` has that id in `itemstatcost.txt`; that row gives the target. Stats with a layer, a value of 0 or no row are dropped and logged. Values are used as they are (the game's raw units, as for `SetListStat`).
- **Needs game:** a map item with known affixes (for example `item_maxhp_percent` 30 and `fireresist` -20, both in `mapstats.txt`) opens with exactly those properties in the log line `ItemStats: 2 item stat(s) read, 2 used`; an item with no stats draws as usual; the item is still intact at the read (the read is before `OpenRedPortal`); an item with 16 and one with 17 or more stats (the note fires only above 16); that the returned list is the affix list and not a state list.


## 15. The map level stat on the item (issue #310)

Build 93847. Reads the same list as section 14 (`ItemListFind` then `ItemListCopy`); no new native part. The plugin looks for the stat `cartographer_map_level` (a new `itemstatcost.txt` row appended by `tools\install.ps1`, id = its row number) in that list. Seen in game (slot 6, Hell, test save, a map item made with `cheat spawn`): a map without the stat logs `map level 85 (the maps.txt Level; the item has no usable map-level stat)` and opens at that level. Cube results (slot 6, Hell, test save, D2R 3.3.0, `cubemain.txt` read from the test mod; a vanilla recipe, 3 Rejuvenation Potions, ran first as the control): a row with input `t20` (or the type `cmap`, or the vanilla misc item `isc`), a second input, `version` 100, `numinputs` 2, output `useitem,mod` and `mod 1` `map-level` 95 consumed the second input and produced a Hand Axe, not a map; the axe's hover showed `Map Level: 95` and the stat survived a save and reload, so the stat row, property and text are right. `useitem` on a misc base therefore rebuilds the wrong base (cause not traced). `usetype,mod`, `usetype,mag,mod` and a plain code output (`t22`) gave maps without the stat (the cube drops a `mod` on a Normal item). Setting the `cmap` type's `Magic` and `Rare` to 1 (also `Normal` 1 and `MaxSockets1` 1 in a second boot) did not change any of this: `useitem,mod` still gave the Hand Axe (`Map Level: 10`), `usetype,mag,mod` and `usetype,rar,mod` still gave plain white maps. Making the cube set the stat on a map would need a plugin hook on the cube result (not written). Not checked: adding to a stat the item already has (the axe was not transmuted again), and whether the stat sits in the `0x40` list the plugin reads (no map ever carried it, so the `from the item's stat` log line was not seen).


## 16. Rarity, affixes and the list layout (issue #311)

Build 93847, D2RLoader 1.3.1-beta, slot 11, test save, 2026-11-12; seen in game. **Correction to sections 14 and 6 C:** D2RLoader's replacement `ItemListCopy` writes 16 bytes an entry, `{int32 layer, int32 stat, int32 value, int32 0}`, not 8-byte `{stat << 16 | layer, value}` pairs; the stat is the second int, the layer the first. Evidence: a unique map with 7 stats returned count 7 and the ints `0 39 15 0, 0 41 15 0, 0 43 15 0, 0 45 15 0, 0 368 95 0, 0 369 30 0, 0 371 -20 0` (the four resists at +15, `cartographer_map_level` 95, `cartographer_mon_life` 30, `cartographer_mon_fire_res` -20). Read as 8-byte pairs the same buffer gave stat 0 (strength) +39, +41, +43, +45 and three layer-15 drops. The buffer is sized for 0x200 entries of 16 bytes. With the corrected decode the open logged `6 item stat(s) read` (the map level taken out), monsters `item_maxhp_percent` +30 and `fireresist` -20, players the four resists +15.

- **Quality:** `cmap` with `Rare` 1, `Magic` 0, `Normal` 0 in `itemtypes.txt` lets the game roll normal or rare, but does not stop magic maps: `Magic` 1 means always magic, so no column blocks them; the plugin hook in section 26 makes a rolled one normal (the check in section 16 was made with Magic on and saw magic maps roll); `Normal` 1 forces Normal. The map's `misc.txt` row must have `compactsave` 0, or the item carries no quality and no stats.
- **Affixes:** `magicprefix.txt` and `magicsuffix.txt` rows with `itype1` `cmap`, and `rareprefix.txt` and `raresuffix.txt` names, were rolled by the game onto `cmap` items spawned with `cheat spawn <code>,typ r|m|lvl N`; the stats land in the base magic list read by `ItemListFind(item, 0, 0x40)`. A unique is a `uniqueitems.txt` row (`code` the map's code) spawned with `typ u`.
- **Hover:** a `descfunc` 19 stat with a plugin-registered key (`cartographer:<key>`, text `%+d%%` with the name) draws on the item; `%+d%%` works.
- **Still open:** stats surviving a Save and Exit and reload, a second-hand or dropped item read, and multiplayer were not checked.
- **Layout guard:** `decodeItemStatList` (statplan, unit tested) takes the buffer only when every entry has a fourth int of 0, a layer of 0 to 0xffff and a stat of 0 to 2047. The 16-byte layout belongs to D2RLoader's replacement, not the game build, so a buffer that does not fit (8-byte pairs, junk) logs `ItemListCopy layout not recognised`, reads no stats and the map opens with the `maps.txt` Level and no modifiers.
